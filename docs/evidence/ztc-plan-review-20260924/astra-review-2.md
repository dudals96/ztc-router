쉬운 요약
지금은 자동화 설비를 더 붙이기 전에 안전 스위치와 계기판부터 검증할 단계다.
설명서에 기능이 있고 프로그램 안에 기능 이름이 있어도 실제 배선과 작동이
확인됐다는 뜻은 아니다. 특히 성능 최적화의 고장 허용과 보안 게이트의
고장 허용은 서로 다른 문제로 다뤄야 한다.

1. 검토 범위와 근거 수준
- 이번 회신에서 인계서, A1~A12 검증 문서, 관련 코드·설정과 현재 공식 문서를 읽었다.
- 설치판의 훅 실행, transcript 원본, 타임아웃·권한 평가 동작은 재현하지 않았다.
- 따라서 기존 문서의 "46건·13 ms" 등은 Claude Code 보고값이며 독립 실측값이 아니다.
- 파일 수정·설치·훅 등록·데몬 기동·commit/push·유료 호출은 이번 검토에서 하지 않았다.
- 이전 턴의 세션 ID 지시문 배포는 별도 작업이며 ZTC 구현 승인으로 간주하지 않는다.
- 아래 V는 docs/evidence/ztc-plan-review-20260924/
  claude-code-verification-A1-A12.md를 뜻한다.
- H는 회신 앞에 링크한 Claude Code 공식 훅 문서다.
  현재 문서의 계약과 설치판 2.1.281의 실제 동작을 구분할 것.

3. A1~A12 판정의 정정·보완
A1 [채택]
- 미해결 ≥20%는 조사 착수 신호다. 모델 도입의 충분조건으로 쓰지 않는다.
- 규칙 개선 대비 순비용·지연·오판정의 증분 효과로 최종 결정한다. 근거: V:9.

A2 [채택, 표현 정정]
- shadow에서 실제 K4는 "0%"가 아니라 "측정 불가/N/A"다.
- 처방이 주입되지 않았으므로 분모 자체가 없다.
- shadow 적합률과 실제 해결·재발 지표를 별도로 유지한다. 근거: V:10.

A3 [채택, 통계 절차 보완]
- 300건→3%p, 1,000건→1%p를 보장하는 표본 규칙은 성립하지 않는다.
- 단일 오류율 상한과 paired 비열등성은 다른 문제다.
- McNemar 검정 이름만 추가해도 해결되지 않는다. paired 차이의 신뢰구간,
  비열등 마진, 검정력, discordance, 세션 내 상관을 사전 지정한다.
- 반복 조정용 데이터와 최종 holdout을 분리한다. 근거: V:11.

A4 [채택, 타임아웃 단정은 거부]
- "중립 반환 ≠ explicit allow" 구분은 유지한다.
- 현재 H의 Timeouts는 PreToolUse command/http/mcp_tool 타임아웃에서
  정상 권한 흐름이 계속되고, SDK callback 타임아웃은 도구 호출을 막는다고 구분한다.
- 따라서 "PreToolUse 타임아웃은 항상 도구 실패"를 공통 계약으로 쓰면 안 된다.
- 설치판·훅 종류별 재현 전에는 해당 동작을 미검증으로 표시한다.
- timeout 초 단위와 클라이언트 내부 예산 분리는 채택하되,
  ≥5초를 근거 없는 공통 안전값으로 확정하지 않는다. 근거: V:12, H.

A5 [채택]
- 문자열 존재는 기능 후보의 증거이고 실행 지원의 증거가 아니다.
- Codex hooks.json 로딩·이벤트·반환 필드 지원은 각각 검증해야 한다.
- Antigravity는 "미확인"을 유지한다. 검색 0건을 미지원 증명으로 쓰지 않는다.
  근거: V:13.
- 추가 정정: "additionalContext는 PostToolUse 전용"은 현재 H와 불일치한다.
  H는 PreToolUse와 PostToolUseFailure 등에도 이를 명시한다.

A6 [채택, 실패 출력 적용은 보류]
- 현재 H는 PostToolUse의 updatedToolOutput을 명시한다.
  따라서 "도구 결과 대체는 언제나 불가능"이라는 단정은 철회해야 한다.
- 다만 PostToolUseFailure에서 같은 교체 필드가 지원된다고 확대 해석하지 않는다.
- 실제 실패가 어느 이벤트로 전달되는지부터 확인해야 M5가 성립한다.
- 실행 비용은 이미 발생했지만 이후 모델 처리량·지연이 줄 가능성은 있다.
  근거: V:14, H의 PostToolUse/PostToolUseFailure.

A7 [채택으로 상향 권고]
- Pi tsconfig에 incremental이 없다는 사실은 전체 작업 동등성을 보장하지 않는다.
- 다른 저장소·도구·ignored 의존성·생성물·외부 설정까지 입력에 영향을 준다.
- 임시 index도 git object 기록과 add 시 필터 처리를 없애지는 않는다.
  "활성 index 보호"와 "무부작용"을 구분한다. 근거: V:15의 제안 방식.

A8 [문제의식 채택, 해결됐다는 표현 거부]
- 별도 worktree만으로 읽기 전용·경합 0·격리가 보장되지 않는다.
- 같은 UID는 원 저장소·홈·자격증명·네트워크에 접근할 수 있다.
- 실제 쓰기 제한, 외부 경로 접근, 공유 캐시와 프로세스 종료 정책이 필요하다.
  근거: V:16. 해당 격리 구현의 실측 증거는 제시되지 않았다.

A9 [채택, 승인 의미 보완]
- 원 결과의 stdout/stderr·종료 상태·입력 지문 보존은 필요하다.
- 치환된 cat이 권한 평가를 통과해도 원 작업에 대한 승인이 증명되지는 않는다.
- 원 명령의 정체성·승인 맥락·캐시 생성 주체·현재 입력 일치를 함께 검증한다.
  근거: V:17.

A10 [원장 채택, 자동 승격 기준 거부]
- "재발 0회가 N=3" 또는 확인 이벤트 하나를 일반적인 자동 승격 조건으로 쓰지 않는다.
- 관측 중단·작업 포기·테스트 미실행도 재발 없음으로 보일 수 있다.
- 성공 재실행과 독립 평가, 적용 범위, 오판정 시 폐기 조건이 필요하다.
  근거: V:18.

A11 [채택, 해결 정의 정정]
- 재발하지 않았다는 사실만으로 해결 판정하지 않는다.
- 목표 검사 성공을 확인하고 포기·관측 종료는 별도로 집계한다.
- CPU·메모리·취소 낭비와 원문 재조회 비용도 순효과에 포함한다. 근거: V:19.

A12 [채택, revision 표현 보완]
- 현재 확인한 구현은 키워드 점수와 합계 나눗셈이며 로짓 추론의 증거가 아니다.
  근거: hierarchical_engine.py:35-64, 93.
- HEAD만 쓰면 미커밋 코드가 빠진다. 판정 대상 파일 해시 또는 diff도 귀속시킨다.
- 기존 UTR의 "로짓 기반 확신도 게이팅 확인"은 해당 근거 범위에서 정정 대상이다.
- 이것을 모든 노드·모든 버전의 부재 증명으로 확대하지 않는다.

4. M1~M6 판정
M1 [채택]
- Windows 전용 명령은 확인된다: .claude/settings.json:105, .codex/hooks.json:9.
- Codex 파일 존재만으로 실제 실행·무력화를 확정하지 않는다.
- "파일 없으면 조용히 통과"는 보안 게이트 복구가 아니다.
- 성능 보조 훅은 실패 시 중립 반환, 필수 보안 게이트는 별도 고장 정책을 정한다.
- 수정 후 금지 명령 차단·허용 명령 통과·게이트 고장 시 동작을 함께 증명한다.

M2 [문제 조사 채택 / 단일 수정으로 해결됐다는 결론 보류]
- biome.json:8-17에는 .codegraph 명시 제외가 없다.
- 하지만 이것만으로 모든 실패 원인이나 --no-verify 상습 사용은 증명되지 않는다.
- 실패 로그와 우회 기록을 첨부하고, 수정 후 원래 품질 게이트 전체를 재검증한다.

M3 [채택, 자동 전파 표현 정정]
- 원자료는 저장소 밖에 두고 보존기간·용량·접근권한을 제한한다.
- git 추적 가능성과 자동 push는 다르다. "매 호출마다 4노드 push"는 별도 증거가 필요하다.
  근거: V:25.

M4 [일부 채택 / 획일적 타임아웃 해석 거부]
- A4 정정을 적용한다. 프로세스 시작·stdin 파싱·연결·응답까지 포함한
  전체 지연과 내부 RPC 예산을 분리해서 측정한다. 근거: V:26, H.

M5 [보류]
- 먼저 성공/실패 이벤트별 교체 가능성을 확인한다.
- 원문 접근권한·보존기간·해시·재조회 수단과 오류 의미 보존을 설계한다.
- 짧아진 바이트 수만으로 청구 토큰 절감이나 작업 품질 유지가 증명되지 않는다.
  근거: V:27, H.

M6 [채택, 경계 확대]
- 데몬 전송·로깅 전에 최소화·마스킹한다. 가능하면 명령 전문을 보내지 않는다.
- 이 조치는 하네스가 이미 저장한 원문까지 소급 제거하지 않는다.
- 명령뿐 아니라 cwd·파일명·stderr·원문 보관 경로도 검토한다. 근거: V:28.

5. 추가로 놓친 관점
- 훅 조합: 다른 훅의 deny·입력 치환·출력 교체와 충돌하는 경우를 검증한다.
- 로컬 신뢰 경계: loopback 바인드만으로 호출자 인증·캐시 변조 방지가 끝나지 않는다.
- 시간차: 분류·프리페치 이후 파일이나 정책이 바뀌면 소비 직전에 무효화해야 한다.
- 과부하: 큐 상한뿐 아니라 중복 작업 합치기·취소 전파·자식 프로세스 회수를 정의한다.
- 정보 경계: 로그에서 추출한 내용은 신뢰되지 않은 데이터다.
  additionalContext로 전달해도 권한 지시나 정책으로 승격하면 안 된다.
- 회복: 오판정 증가·승인 흐름 변화·지연 초과 시 즉시 비활성화할 조건과 복귀 절차가 필요하다.
위 항목은 추가 설계 검증 요구이며, 현재 장애를 실측했다는 뜻은 아니다.

6. Phase 1 첫 3작업 권고
1) 계약·근거 정정: 위 반증을 반영하고 버전/훅 종류/이벤트별 검증표와 KPI를 확정한다.
2) 승인된 범위에서 오프라인 안전화: M1 보안 게이트, 품질 게이트, 마스킹,

   정상/부재/오류/취소/과부하와 기존 승인 보존을 관찰한다.

7. 전환 조건과 사용자 결정
- shadow → additionalContext: 적합률·오처방·지연 기준 충족과 데이터 취급 검증 후 승인.
- additionalContext → deny와 updatedInput: 별도 트랙으로 심사한다.
  deny는 오차단·회복, updatedInput은 의미 동등성·원 권한 보존이 각각 필요하다.
- 결정 요청: Phase 1 범위·우선순위, 보안 게이트 고장 정책, 정정 문서 반영,
  shadow 등록 여부. 설치·launchd·Windows 추측 실행 승인을 묶지 않는다.
- Claude Code는 반대 항목별로 동의/반박/미확인과 증거 수준을 회신할 것.
- 구현·설정 변경 없이 사용자 다음 지시를 기다릴 것.
